# Queue pressure — approved backend extension, 17 October 2026

The user's request for dynamic queue pressure explicitly supersedes the older redesign requirement to leave all backend code untouched. Existing order states, payment eligibility, pricing and pickup code contracts are unchanged.

Closed shops return `rush_level: null`, `rush_basis: "closed"` and no clearance estimate. Manual status, timed Busy and IST business hours use the existing `computeShopAvailability` source. The list, comparison, shop detail and standalone queue endpoint all use the same calculation. Customers must also suppress rush for a closed shop when reading an older server or a local fixture.

`active_orders_count` retains its earlier meaning: paid pending, accepted and ready-for-pickup orders. New `queued_orders_count` counts only paid pending/accepted orders. `ready_orders_count` separates the collection backlog: finished prints must not inflate production pressure. Cancelled, expired and unpaid orders never consume queue capacity.

No reliable production timestamps existed in this schema. `updatedAt` changes at collection, settlement and other writes; completed-order cadence measures customer collection rather than printer output. The additive nullable `Order.ready_at` is now stamped only by the actual accepted → ready-for-pickup action, through one atomic compare-and-set requiring accepted status and a null/missing timestamp. Duplicate requests cannot overwrite it or emit another transition. Historical orders remain null. There is deliberately no invented backfill or new workflow stage.

For each shop, a rolling **60-minute** window measures work marked ready. At least **five** jobs, timestamps spanning **ten minutes**, and a last ready transition within **15 minutes** are required. The rate uses the interval between first and last observed ready timestamps, excluding the first job’s workload: its preparation happened before the observed interval. This prevents fifty idle minutes from diluting ten minutes of fast output. The ten-minute minimum guards short bursts, but batch marking can still distort the rate; this is observed output cadence, not independently measured machine capacity. Output uses a documented workload proxy: **five setup units per order + page count × copies + ten units per finishing selection**. These are heuristic operational weights, not measured machine timings; duplex, paper, colour and different finishing complexity are not individually calibrated. This avoids treating a 500-page batch as equivalent to a single page while keeping the model inspectable. Offline jobs are not tracked. Batch ready clicks, limited history and abrupt capacity changes can still make estimates inaccurate.

Estimated clearance is queued workload divided by observed units/minute, rounded up and capped at **240 minutes**. It is a queue clearance estimate, **not a new order's promised pickup time**; that order's own work and vendor Busy guidance remain separate. Rush is low at ≤15 minutes, medium at ≤35, high above. A large queue at a shop with fast output can therefore be low pressure. Thresholds are absolute and independent of other shops, so every shop being busy does not make the least busy one falsely low through relative ranking.

When evidence is sparse/stale, `rush_basis: "queue_count"` and `throughput_confidence: "insufficient"` retain the existing admin `rush_thresholds.low_max/medium_max`, applied to the waiting production queue. No fabricated ETA is returned. Existing admin controls are global count thresholds, not a per-shop rush override. Vendor Open/Busy/Closed and Busy preparation guidance remain independent. Admin settings copy now explains when its thresholds apply.

Additive response fields: `queued_orders_count`, `ready_orders_count`, nullable `estimated_clearance_minutes`, `rush_basis` (`closed`, `queue_count`, `recent_throughput`), `throughput_confidence` (`unavailable`, `insufficient`, `observed`), `throughput_sample_orders`, `throughput_window_minutes`. `observed` describes the evidence gate, not statistical certainty. Clients must not turn `null` into zero or label clearance as guaranteed preparation time.

The batch service performs two aggregate queries plus the existing cached settings read for any number of shops. Aggregations return only per-shop numeric summaries; no filenames or customer data. A compound `(shop_id, payment_status, ready_at)` index supports the rolling window. Empty lists issue no queries. Existing print queue position logic is unchanged.

The loopback phone fixture now reuses the production pure calculator and workload function on its current prebuilt and newly created orders. List, detail, standalone queue, saved shops, comparison and embedded order-shop responses derive live counts consistently. The prebuilt order starts accepted/paid without a fabricated ready timestamp; marking it ready through the QA state endpoint records the real current time once. Unpaid new orders are excluded. `node --test userapp/qa/fixture-queue.test.cjs` exercises count/state distinctions and all response surfaces using an isolated ephemeral HTTP server, leaving the phone's active fixture process untouched.

Validation: `node --test backend/scripts/queuePressure.test.js` covers closed suppression, sparse/stale/burst/future samples, configured fallback, high-count fast versus low-count slow output, workload size/finishing, capped estimates, ready collection backlog, paid/status filters, constant batch query count, atomic ready compare-and-set and fast output after fifty idle minutes. A giant first job is excluded from the rate to avoid inflating capacity from work completed before observation. This test suite uses a database seam; no production database, live printer or live Mongo aggregation was exercised. The phone's disposable fixture does not create production throughput history automatically.
